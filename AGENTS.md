# trellis-tiny

This repository is trellis-tiny: a lightweight project workflow for Claude Code and Codex, written in Python with only the standard library. It replaced an earlier TypeScript implementation, the `tiny/` npm package, which has been removed.

## Start here

- `docs/design.md` is the design record. Section 8 lists confirmed decisions and section 9 the open questions. Read the relevant sections before changing behavior, and update the document when a design decision changes.
- `README.md` explains installation and use.
- Run the tests before and after a change: `python -m unittest discover -s tests`. They run `tt.py` end to end against throwaway Git repositories.

## Layout

- `ttlib/` is the implementation. `ttlib/assets/` holds what `tt init` installs into a project: the AGENTS.md managed block, the six `tt-*` skills, the reviewer subagent, and the templates.
- `tests/` holds the test suite.
- `tt`, `tt.cmd`, and `tt.py` are the launchers and the entry point. `./tt install` puts the `tt` command on PATH.
- `docs/zh/` holds Chinese reading copies of the managed block, the skills, and the reviewer. When you change the English source in `ttlib/assets/`, update the matching copy.
- `.trellis/tiny/`, `.claude/`, `.codex/agents/`, and `.agents/skills/` are tiny-trellis as installed into this repository for its own workflow, by `tt init`. Change the source in `ttlib/`, never these copies.

## Conventions

- Runtime code uses only the Python standard library and must run on Python 3.9.
- `tt` keeps LF line endings and `tt.cmd` keeps CRLF, as `.gitattributes` enforces; a launcher with the wrong endings does not run.
- Don't push to the remote. The user pushes, and a push to `main` runs CI.

## Project workflow (tiny-trellis)

This project keeps its conventions, cross-session tasks, and change journal under `.trellis/`. These rules are for the main session; a subagent follows only the instructions in its own task.

- **Commands** run as `<prefix> <command>`; the tiny-trellis status line at session start shows the prefix. If there is no status line in your context, the startup hook did not run: run `.trellis/tiny/tt.py status` with whichever of `python3`, `python`, `py` exists, and tell the user the hook is not working.
- **Knowledge**: before changing an area, read `.trellis/spec/index.md`, then only the files that apply. `.trellis/workspace/` is the journal; `finish` writes it, so don't edit it by hand.
- **Sizing**: an explicit level from the user wins. Otherwise, work that likely won't finish in this session is cross-session (`tt-task`), a request with a choice only the user can make needs `tt-clarify` first, and everything else is small: do it, then finish it. A change to a public interface, a data migration, security, or a bulk deletion also needs `tt-review`. Move up as soon as work turns out larger; moving down needs the user's agreement.
- **Finishing**: when a change is complete, including each verified step of cross-session work, run `finish --reason "<why this change>" --verify "<command that shows it works>" --review self|independent`. You can't see when a session ends, so don't save this for the end. Use `--no-verify "<why>"` only when nothing is executable, such as a docs-only change. If `finish` fails, fix the cause and run it again; weakening the check or the command hides the failure.
- **Checks**: when a tiny-trellis check blocks the end of a turn, fix what it reports. The checks in `.trellis/tiny/checks/` are project rules; change them only when the user asks.
- **Recording**: when the user confirms a decision later work must follow, or a fix teaches a lesson worth keeping, use `tt-record`. The user starts `tt-digest` (old material into specs) and `tt-bootstrap` (first specs) when they want them.
