# Trellis Meta

This skill is for local trellis-tiny users who have already run `tt init` in a project. After reading it, an AI should understand the trellis-tiny architecture, operating model, and customization entry points inside that user project, then modify the generated `.trellis/` and platform directory files according to the user's request.

trellis-tiny is a slimmed-down Trellis distribution: three supported platforms (codex / zcode / dsh), one shared skill root, a zero-task fast path for simple work, and no channel system. Cross-session memory stays first-class: `tt mem list | search | context | extract | projects` reads raw agent JSONL already on disk, slices by `--phase brainstorm|implement|all`, and never uploads anything. Everything ships as one npm package, `trellis-tiny` (CLI command `tt`).

The default operating scope is local files in the user project:

- `.trellis/`: workflow, config, tasks, spec, workspace, scripts, and runtime state.
- Platform directories: `.codex/`, `.zcode/`, `.dsh/` — plus the shared `.agents/skills/` skill root all three platforms read. ZCode injects context through `.zcode/hooks/` registered in `.zcode/config.json`; codex registers hooks via `.codex/hooks.json`; dsh is pull-based with its three command-entry skills under `.dsh/skills/`.
- Raw platform conversation logs queryable via `tt mem`: `~/.claude/projects/`, `~/.codex/sessions/`, `~/.pi/agent/sessions/`, and more.

Do not assume the user has the trellis-tiny source repository. Do not default to modifying the global npm install directory or `node_modules` — trellis-tiny ships as a published package.

## How To Use

1. Read `references/local-architecture/overview.md` first to establish the local Trellis system model.
2. If the request involves a specific AI tool, read `references/platform-files/platform-map.md` and the relevant platform file notes.
3. If the user wants to change behavior, read `references/customize-local/overview.md`, then open the specific customization topic.
4. Before editing, read the actual files in the user project and treat local content as authoritative.

## Current Rules

- `.trellis/workflow.md` is the local workflow source of truth; its content ships inside the trellis-tiny package (`src/templates/trellis/workflow.md`) and was written by `tt init`. There are no selectable workflow variants or marketplace templates — edit the file directly; `tt update` will then treat your edits as user modifications and ask before overwriting.
- `.trellis/config.yaml` is the project-level trellis-tiny configuration entry point. It hosts task lifecycle hooks (`hooks.after_create` / `after_start` / `after_finish` / `after_archive`), journal shape (`session_commit_message` / `max_journal_lines` / `session_auto_commit`), and Codex dispatch mode (`codex.dispatch_mode: inline | sub-agent`).
- `.trellis/spec/` stores the user's project-specific coding conventions and design constraints. The generic template set is written once by `tt init`; after that the directory is treated as user assets — `tt update` never overwrites or removes it. Templates are plain files, so edit them directly; upgrades ship updated templates only for fresh installs.
- `.trellis/tasks/` stores task PRDs, design notes, implement plans, research files, and JSONL context. Tasks form parent/child trees: `task.py create --parent <slug>`, `task.py add-subtask <parent> <child>`, `task.py remove-subtask <parent> <child>`, and `task.py list-context <task>`. `task.py create` rejects a slug already present in `.trellis/tasks/archive/**`. Simple tasks may skip `.trellis/tasks/` entirely — the workflow's zero-task fast path runs them inline.
- `.trellis/workspace/` stores **deliberately written** developer journals. Raw cross-session dialogue is **not** stored here — it lives on disk under `~/.claude/projects/`, `~/.codex/sessions/`, `~/.pi/agent/sessions/` and similar paths, and is recovered via `tt mem search|extract|context`. The bundled `trellis-session-insight` skill teaches when to reach for `mem`.
- Bundled multi-file skills (`trellis-meta`, `trellis-spec-bootstrap`, `trellis-session-insight`) are auto-dispatched to the shared `.agents/skills/` root — the single skill root for codex / zcode / dsh — by `getBundledSkillTemplates()` in `src/templates/common/index.ts`. Dropping a new directory under `src/templates/common/bundled-skills/` ships it on the next `tt update`.
- Platform settings/config files decide which hooks, agents, skills, commands, prompts, and workflows actually run. ZCode reads `.zcode/config.json`; codex additionally needs `features.hooks = true` in the user's global `~/.codex/config.toml`.
- `.trellis/.template-hashes.json` and `.trellis/.runtime/` are management/runtime state files. Confirm necessity before editing them.

## Do Not

- Do not treat trellis-tiny upstream source code as the default target for local customization.
- Do not modify the global npm install directory or `node_modules/trellis-tiny` to implement project needs.
- Do not overwrite user-modified local files with default templates; check `.trellis/.template-hashes.json` first and prefer `.new` sidecar files over destructive overwrites.
- Do not put team-private project rules into any public bundled skill (`trellis-meta`, `trellis-spec-bootstrap`, `trellis-session-insight`); put project rules in `.trellis/spec/`, a project-local skill, the current task, or the workspace journal — `tt update` will overwrite anything inside a bundled skill directory.
- Do not describe removed or never-shipped mechanisms as current behavior; cross-check against the local `.trellis/config.yaml` and the installed CLI's `tt --help` before claiming a knob exists.
