## 项目工作流（tiny-trellis）

本项目把约定、跨会话任务和改动日志保存在 `.trellis/` 下。这些规则只约束主会话；子代理只按自己任务里的指令行事。

- **命令**的运行形式是 `<前缀> <命令>`；会话开始时的 tiny-trellis 状态行会给出前缀。如果上下文里没有状态行，说明启动 hook 没有运行：用 `python3`、`python`、`py` 中本机存在的那个运行 `.trellis/tiny/tt.py status`，并告诉用户 hook 没有生效。
- **知识**：修改某个区域之前，先读 `.trellis/spec/index.md`，再只读适用的文件。`.trellis/workspace/` 是日志，由 `finish` 写入，不要手动编辑。
- **判定规模**：用户明确声明的级别优先。否则，很可能在本次会话内做不完的工作属于跨会话任务（`tt-task`）；需求里有只有用户能做的选择时，先用 `tt-clarify`；其余都是小任务：直接做，然后收尾。涉及公共接口、数据迁移、安全或批量删除的改动，还需要 `tt-review`。一旦发现工作比预想的大，立即升级；降级需要用户同意。
- **收尾**：一项改动完成时，包括跨会话任务中每个已验证的步骤，运行 `finish --reason "<为什么做这个改动>" --verify "<能证明它有效的命令>" --review self|independent`。你看不到会话何时结束，所以不要把这一步留到最后。只有在没有任何可执行的验证时（例如只改了文档），才使用 `--no-verify "<原因>"`。如果 `finish` 失败，修复原因后重新运行；放宽检查或验证命令只会把失败藏起来。
- **检查**：当 tiny-trellis 的检查阻止一轮对话结束时，修复它报告的问题。`.trellis/tiny/checks/` 里的检查是项目规则；只有用户要求时才修改它们。
- **记录**：当用户确认了一个后续工作必须遵守的决定，或者一次修复得出了值得保留的经验时，使用 `tt-record`。`tt-digest`（把旧材料整理成规范）和 `tt-bootstrap`（建立第一批规范）由用户在需要时启动。
