# Trellis 轻量版设计（工作名 tiny-trellis）

状态：设计草案，未实现。更新日期：2026-11-18。首批平台：Claude Code、Codex。实现语言：Python，仅用标准库。

文中的命令名、文件名均为草案。平台能力一节的事实已对照官方文档或源码核实，来源见文末；标注"待核实"的内容尚无依据。

## 1. 要解决的问题

Trellis 让小任务和大任务付同样的固定成本：每次会话注入流程手册，每轮对话注入状态，实现和审查各派一个冷启动子代理并重复注入规范。mini-trellis 的做法是删掉整个任务层，上下文成本降下来了，但规范是否被遵守完全依赖模型记得去检索，跨会话任务也失去了交接记录。

本设计要同时满足三个要求：

- 上下文成本是首要削减对象。
- 不允许漏掉规范。
- 流程走多重由模型判断，用户可以显式声明覆盖。

做法分三部分：

- **管理方案写进项目级提示词。** 它是一段固定文字，以受管块的形式放在项目的 `AGENTS.md` 里，由平台原生加载，压缩后平台会重新注入，不依赖 hook。
- **动态状态由一个小 hook 补充。** 进行中的任务、上次未记录的改动这类会变的内容，由启动 hook 输出一行状态。
- **操作步骤放在技能里。** 澄清需求、跨会话任务、独立审查、记录知识等步骤写成技能，平时只有描述常驻上下文，用到时才加载正文。
- **事后用确定性的方式核对。** 项目登记的检查脚本每轮结束时自动运行，验证命令在收尾时由 CLI 执行并记录真实结果。

## 2. 范围

**全局提示词不在 tiny-trellis 的范围内。** `~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md` 这类用户级指令由平台在每个会话中必然加载，tiny-trellis 不读取、不复制、不检查它们，也不为其中的规则安装任何拦截或检查。

tiny-trellis 只负责项目内的三件事：项目的管理方案、项目知识（规范、调研、任务、日志）、项目自己登记的检查。

## 3. 系统行为

### 3.1 会话开始

- 平台加载全局提示词（与本工具无关）和项目级提示词。项目级提示词里的受管块告诉模型：流程如何分级、何时创建任务、怎样收尾、项目知识在哪里。
- 启动 hook 调用 CLI 输出一行状态：本机调用 CLI 的命令前缀，以及进行中的跨会话任务、"上次会话有未记录的改动"提示（如有）。没有任务和提示时也输出这一行，这样模型能分辨出 hook 没有运行的情况；命令前缀因机器而异，不能写进随仓库共享的受管块。

之后每轮对话不再注入任何内容。上下文被压缩后，两个平台都会重新注入项目级提示词，启动 hook 也会再次运行。

### 3.2 执行任务

模型按受管块中的判据自行判定任务级别，用户的显式声明优先。默认由主代理自己实现，不派发实现子代理。长文知识（规范细节、调研结论）不注入，模型需要时按受管块给出的索引读取。

### 3.3 每轮结束

一轮指用户发出一条消息、agent 工作并回复后停下。如果项目登记了检查脚本，agent 每次准备停下时，结束 hook 自动运行这些脚本，检查对象是自上次检查以来的改动。这一步由平台触发，不依赖模型记得去做。

- 全部通过时不输出任何内容，上下文不增加。
- 有检查不通过时阻止结束，并把检查名称和位置告诉模型，模型修复后才能停下。

项目没有登记任何检查时，不安装结束 hook。

### 3.4 收尾

模型调用收尾命令，CLI 依次做三件事：

1. 复跑项目登记的检查，任何一项不通过则命令失败。
2. 执行模型给出的验证命令，记录真实的退出码和输出摘要。
3. 以上都完成后，向日志追加一条记录。

收尾时由模型对照任务目标和验收标准自检；高风险改动另派独立上下文审查，见 4.1。

### 3.5 跨会话

模型判定任务会跨会话时，创建一个单文件任务记录，写明目标、验收标准、已完成部分、下一步和中途做的决定。新会话中启动 hook 会指向它，模型读取后继续。

## 4. 条件与结果

### 4.1 流程分级

| 级别 | 判定条件 | 流程 | 落盘内容 |
|---|---|---|---|
| 小任务 | 需求无歧义，预计本次会话完成，不改公共接口、数据结构或依赖 | 直接执行，收尾核对 | 一条日志 |
| 跨会话任务 | 预计跨会话，或需求存在需要用户确认的歧义 | 先写目标和验收标准，再执行 | 任务文件，加日志 |
| 高风险改动 | 涉及公共接口、数据迁移、安全、批量删除 | 在上面任一流程之上，加独立上下文审查 | 审查结论并入日志 |

- 判据写成可观察的条件，是因为要支持多种模型，能力弱的模型倾向于低估任务规模。
- 执行中发现规模超出预期可以随时升级；降级需要用户同意。
- 用户未声明时，完全由模型判断。

### 4.2 项目检查

| 条件 | 结果 |
|---|---|
| 项目没有登记检查 | 不安装结束 hook，收尾时跳过检查步骤，日志记为"无项目检查" |
| 自上次检查以来没有改动 | 直接退出，不运行检查脚本 |
| 全部通过 | 不输出，不占上下文 |
| 有检查不通过 | 阻止结束，告知检查名称与位置 |
| 同一失败在模型未修复的情况下再次出现 | 放行，向用户显示警告，避免死循环 |
| 检查脚本自身出错 | 阻止结束并报出错误，不静默放过 |

检查脚本只能判定脚本能判定的事，比如扫描密钥、运行 lint。需要读代码判断的要求留在规范或受管块里，由模型在收尾时对照。

### 4.3 收尾与记录

| 条件 | 结果 |
|---|---|
| 项目检查不通过 | 收尾命令失败，不写日志 |
| 验证命令退出码非零 | 收尾命令失败，不写日志，模型修复后重跑 |
| 改动没有可执行的验证（如只改文档） | 明确记为"无验证"，不留空 |
| 小任务或跨会话任务 | 由主代理对照目标和验收标准自检，日志记为"自检" |
| 高风险改动，或用户要求 | 派独立上下文的审查子代理，日志记为"独立审查" |
| 会话结束时没有调用收尾命令 | 下次会话的启动 hook 提示存在未记录的改动 |

最后一行是对"流程交给模型判断"的补偿：不强制模型收尾，但漏掉的收尾在下次会话一定会被看见。检测方式是比对当前 Git 状态与最后一条日志记录的状态，因此本工具要求项目是 Git 仓库。

### 4.4 受管块的写入

| 条件 | 结果 |
|---|---|
| 项目没有 `AGENTS.md` | 新建文件，只含受管块 |
| 项目已有 `AGENTS.md` | 在文件末尾追加受管块，原有内容不动 |
| 已有受管块 | 只替换开始与结束标记之间的内容 |
| 项目已有 `CLAUDE.md` 但没有导入 `AGENTS.md` | 在文件开头加一行 `@AGENTS.md` |
| 项目没有 `CLAUDE.md` | 新建一个只含 `@AGENTS.md` 的 `CLAUDE.md` |
| 任何写入 | 先能用 `--dry-run` 预览，写入不删除任何已有内容 |

没有 `CLAUDE.md` 时 Claude Code 本可以直接读取 `AGENTS.md`，但文档列出了它读不到的情况（如升级后的第一个会话、相关内置插件被关闭）。为了不漏掉管理方案，统一用导入的方式。

## 5. 具体例子

### 5.1 受管块的位置

```markdown
（项目原有的 AGENTS.md 内容）

<!-- tiny-trellis:begin -->
（管理方案正文：流程分级判据、何时建任务、收尾命令、知识索引）
<!-- tiny-trellis:end -->
```

正文见 [ttlib/assets/agents-block.md](../ttlib/assets/agents-block.md)，中文对照见 [zh/agents-block.zh.md](zh/agents-block.zh.md)。草稿用英文，与全局提示词一致。操作步骤移入技能后，正文从约 3,660 字符缩减到约 2,200 字符，占 Codex 默认 32 KiB 合计上限的 7%。

正文开头声明它只约束主会话。原因是 Claude Code 的自定义子代理也会加载它，但子代理没有启动 hook 的状态行，不加这句会误以为 hook 失效。

### 5.2 每轮检查拦住一次违规

项目登记了一个密钥扫描脚本。用户让 agent 增加支付回调功能，agent 把接口密钥直接写进了 `config.py`，准备回复"已完成"。

1. agent 准备停下，结束 hook 运行检查脚本。
2. 密钥扫描在 `config.py` 第 12 行发现密钥，检查不通过。
3. 平台阻止结束，agent 收到"密钥扫描未通过，位置 config.py 第 12 行"。
4. agent 改为从环境变量读取，再次准备停下，检查通过，正常回复用户。

### 5.3 小任务的一条日志

```markdown
## 2026-11-17 14:32 修复回调重复投递
- 级别: 小任务
- 原因: 重复回调导致重复扣款，改为按幂等键返回首次结果
- 改动: src/callback/handler.py, tests/test_callback.py
- 验证: `pytest tests/test_callback.py -q`，退出码 0，12 passed
- 项目检查: 2/2 通过
- 审查: 自检
- 提交: a1b2c3d
```

"原因"由模型提供一句话；日期、改动文件、验证结果、检查结果、提交号由 CLI 采集。

### 5.4 跨会话任务文件

```markdown
# 回调重试策略重构
- 状态: 进行中
- 目标: 幂等的瞬时失败最多重试 4 次，其余不重试
- 验收标准: 新增的 8 个用例全部通过；旧接口签名不变

## 已完成
- attempt_limit 实现与单元测试

## 下一步
- 接入回调调度器

## 决定
- 永久失败保持 1 次，原因见 spec/callback.md
```

### 5.5 独立审查的交接内容

主会话只交给审查子代理三样东西：任务目标、验收标准、改动范围（提交区间或文件列表）。不交实现过程，不交规范全文。子代理按自己加载的提示词和读到的规范审查，返回发现的问题。

定义文件见 `ttlib/assets/reviewer.md` 和 `ttlib/assets/reviewer.toml`，两份的指令正文逐字相同，中文对照见 [zh/reviewer.zh.md](zh/reviewer.zh.md)。回复格式固定为四部分（结论、验收标准逐条、发现、未检查），每条发现标明"已确认"或"判断"，与日志区分事实和模型判断的原则一致。名称用下划线 `tiny_trellis_reviewer`，因为 Codex 文档的示例用下划线，连字符是否可用没有说明。

## 6. 边界与误区

**不是每个阶段都需要子代理。** 子代理只在两种情况下划算：检索范围大到会污染主上下文，或需要没看过实现过程的独立审查。实现阶段派子代理会丢掉主代理在规划时积累的上下文，只能重新注入，这正是 Trellis 重复注入成本的主要来源。

**项目级提示词同样只是上下文。** Claude Code 的文档写明，`CLAUDE.md` 是上下文而不是强制配置，不保证被严格遵守。受管块越短、越具体，越容易被遵守；真正的保证只来自检查脚本和验证命令。

**受管块的成本由每个会话支付。** 它在每个会话开始时加载，Claude Code 的自定义子代理默认也会加载它。所以它只写"怎么做"，不写长文知识，长文知识按需读取。

**tiny-trellis 不保护全局规则。** 全局提示词里的规则（例如不执行破坏性 Git 操作）由平台加载、由模型遵守，tiny-trellis 不检查也不拦截。如果需要强制，应在用户级自行配置平台的 hook，与本工具无关。

**"自检"和"独立审查"的结论仍然是模型的判断。** 日志如实记录是哪一种，不把它表述为已验证的事实。只有检查脚本和验证命令的结果是事实。

**不强制每轮核对全部要求。** 一轮结束不等于任务结束。多轮任务里每轮都要求模型做完整核对并写日志，等于每轮都付一次审查的上下文成本，而查出来的结论仍然是模型的判断。

**不做的事。** 不设每轮注入，不设阶段和流程手册，不设独立的需求文档文件，不做向量检索，不读取各平台的原始对话记录，首批不支持 Claude Code 和 Codex 之外的平台。

**操作步骤放在技能里，不放在受管块里。** 早期草案不使用技能层，理由是不依赖各平台的技能目录约定。2026-11-19 改为使用技能：技能平时只有描述常驻上下文，正文在用到时才加载，比把步骤写进每个会话都全量加载的受管块更符合"按需读取"。受管块只保留每次都适用的规则，并指明什么情况用哪个技能，见 7.7。

**迁移不删除任何文件。** 项目已装有上游 Trellis 时，`init --migrate` 先迁移再安装，可以用 `--dry-run` 预览。上游安装了哪些文件，以它自己的安装清单 `.trellis/.template-hashes.json` 为准；这些文件移入 `.trellis/archive/upstream-<时间>/`，保持原有相对路径。共用文件里只摘掉上游的部分，摘下的内容原样记入归档目录的 `MIGRATION.md`。`spec/`、`tasks/`、`workspace/` 原地不动，旧任务只生成一份索引，不让模型批量整合，等检索命中旧材料时再按需整理。mini-trellis 的迁移不创建备份且永久删除文件，本设计明确不采用这种做法。

原设想是把旧任务目录移入归档，实现时改为原地保留，因为移动会让旧笔记里的相对链接失效。

**Codex 的 hook 可能静默失效，但不影响管理方案本身。** Codex 的 hook 需要经过信任审查，信任按内容哈希记录，hook 一旦变动就会被跳过直到重新信任。管理方案在 `AGENTS.md` 里，不受影响；受影响的只有动态状态和项目检查。应对方式：hook 命令固定为一行对 CLI 的调用，升级时内容不变；受管块里留一句说明，要求模型在看不到状态行时主动运行状态命令，并告诉用户 hook 没有生效。

**启动速度不是选型依据。** 每轮结束最多运行一次脚本。2026-11-17 在一台 Windows 10 机器上实测，Python 3.15 启动加常用标准库模块导入约 60 到 100 毫秒，相对一轮对话可以忽略。如果以后加入每次工具调用都触发的 hook，这个结论需要重新评估。

## 7. 术语与文件对应

### 7.1 磁盘上的内容

| 术语 | 位置（草案） | 说明 |
|---|---|---|
| 管理方案 | 项目 `AGENTS.md` 中的受管块 | 固定文字，每个会话由平台加载 |
| Claude Code 入口 | 项目 `CLAUDE.md` 中的 `@AGENTS.md` | 让 Claude Code 加载同一份受管块 |
| 长文知识 | `.trellis/spec/` | 沿用 Trellis 已有的规范文件，按需读取 |
| 调研笔记 | `.trellis/spec/research/` | 规则背后的证据和被放弃的方案，由规则链接过去；不列入知识索引 |
| 知识索引 | `.trellis/spec/index.md` | 每个规范或调研文件一行说明；模型先读索引，再只读适用的文件 |
| 任务 | `.trellis/tasks/<日期>-<名称>.md` | 仅跨会话任务才创建，单文件，由 `task new` 按模板生成 |
| 日志 | `.trellis/workspace/<开发者>/tiny-journal.md` | 只追加，每次收尾一条；跨会话任务每个会话至少一条，并链接任务文件。开发者目录名取自 `git config user.name`，除字母、数字、点和连字符以外的字符换成连字符 |
| 审查子代理 | `.claude/agents/tiny_trellis_reviewer.md`、`.codex/agents/tiny_trellis_reviewer.toml` | 由 `init` 写入；源文件在 `ttlib/assets/` |
| 项目检查 | `.trellis/tiny/checks/` | 项目登记的检查脚本，可以没有 |
| 工具脚本 | `.trellis/tiny/` | CLI 的项目副本，hook 调用的就是它，随仓库提交 |
| 安装记录 | `.trellis/tiny/config.json` | 安装的版本和平台，随仓库提交；有它就表示已安装 |
| 所有权清单 | `.trellis/tiny/manifest.json` | tt 整体写入的文件及其哈希，随仓库提交，升级时据此判断文件是否被手动改过 |
| 升级备份 | `.trellis/tiny/.backup-<时间>/` | 升级时被替换或退役的文件，不提交 |
| 运行时状态 | `.trellis/tiny/.runtime/` | `local.json`（本机解释器与 shell）和 `state.json`（基线快照、上次通过检查时的快照、已阻止过的失败），不提交 |
| 基线引用 | `refs/worktree/tiny-trellis/last-finish` | 指向基线快照的提交，防止 `git gc` 回收；每个工作树各一份，默认不会被推送 |
| 本机排除规则 | `.git/info/exclude` | 加入 `/.claude/settings.local.json` 和 `/.codex/hooks.json`；两者含本机路径，不进 Git |
| 上游归档 | `.trellis/archive/upstream-<时间>/` | 仅迁移时创建：移走的上游文件、`MIGRATION.md`，以及让归档文件不被上级规则忽略的 `.gitignore` |
| 旧任务索引 | `.trellis/spec/upstream-tasks.md` | 仅迁移时创建：每个上游任务一行，链接到它的 `prd.md` 或任务目录 |
| 技能（Claude Code） | `.claude/skills/tt-*/SKILL.md` | 6 个技能；仅用户调用的两个在头部多一行 `disable-model-invocation: true` |
| 技能（Codex） | `.agents/skills/tt-*/SKILL.md` | 与源文件相同；仅用户调用的两个另有 `agents/openai.yaml` |

日志文件与上游 journal 文件的具体兼容方式待读上游源码后确定。

### 7.2 命令（草案）

| 命令 | 作用 |
|---|---|
| `tt init [--claude] [--codex] [--migrate] [--dry-run] [--force \| --keep] [--allow-downgrade]` | 未安装的项目：全新安装，不带平台参数时两个平台都装。已安装的项目：升级到本机 tt 的版本，见 7.8。所有新内容先算好再写，任何一处出错都不改动文件。项目装有上游 Trellis 时必须加 `--migrate`，先迁移再安装 |
| `tt.py status [--hook]` | 输出一行状态：命令前缀、进行中的任务、未记录改动的文件数 |
| `tt.py check [--hook]` | 手动运行项目检查；带 `--hook` 时作为结束 hook，失败以退出码 2 阻止结束 |
| `tt.py finish --reason ... (--verify CMD \| --no-verify WHY) --review self\|independent [--task NAME]` | 复跑检查，执行验证命令，写日志；自上次收尾以来没有改动时拒绝执行 |
| `tt.py task new TITLE` / `task close NAME` | 创建、结束跨会话任务 |

调用形式为"本机解释器 + `.trellis/tiny/tt.py` + 命令"，解释器部分由状态行告诉模型。`finish` 不做 Git 提交，只记录当时的提交号和工作区状态。

### 7.3 平台能力对应

| 能力 | Claude Code | Codex |
|---|---|---|
| 项目级提示词 | 读取项目 `CLAUDE.md`；没有 `CLAUDE.md` 时读取 `AGENTS.md`（v2.1.277 起）；`CLAUDE.md` 中的 `@AGENTS.md` 会导入它 | 从项目根向当前目录逐级读取 `AGENTS.md`，拼接在全局文件之后 |
| 压缩后 | 项目根 `CLAUDE.md` 从磁盘重新注入；导入的文件与导入它的 `CLAUDE.md` 一起加载，由此推断受管块也会回来，未实测 | 源码显示压缩后会把含 `AGENTS.md` 指令在内的初始上下文重新插入历史 |
| 大小限制 | 建议每个 `CLAUDE.md` 少于 200 行；导入不降低上下文成本 | 全局与项目文件合计默认上限 32 KiB（`project_doc_max_bytes`），超出部分不再加入 |
| 动态状态 | `SessionStart` hook，配置在 `.claude/settings.json`；压缩后以 `compact` 再次触发 | `SessionStart` hook，配置在 `.codex/hooks.json`；匹配 `source: "compact"` 的 hook 在下一次模型请求前运行 |
| 每轮结束的检查 | `Stop` hook，每轮触发，不支持匹配器；退出码 2 阻止结束并继续对话 | `Stop` hook，匹配器不生效；退出码 2 加 stderr 中的原因让 Codex 继续，原因成为新的提示 |
| 检查脚本以其他退出码失败时 | 待核实 | 文档未说明 |
| 向用户显示警告 | 待核实 | 输出中的 `systemMessage` 会作为警告显示 |
| hook 生效前提 | 文档未提及信任步骤 | 需经 `/hooks` 审查信任；项目级 hook 还要求 `.codex/` 层被信任 |
| hook 命令的执行方式 | 带 `args` 时直接启动程序，不经过 shell；不带时在 Windows 上交给 Git Bash，未安装则交给 PowerShell | 待核实 |
| Windows 专用命令 | 没有对应字段 | `commandWindows` 可单独覆盖 Windows 上的命令 |
| 独立审查 | `.claude/agents/*.md`，全新上下文，看不到主会话历史 | `.codex/agents/*.toml`，独立线程；是否继承父会话对话，文档未说明 |
| 审查方加载的提示词 | 自定义子代理默认加载全部 `CLAUDE.md` 层级及作为项目指令加载的 `AGENTS.md`；内置 Explore 和 Plan 不加载 | 文档未说明 |
| 委派触发 | 模型按子代理的 `description` 委派 | 仅在用户直接要求，或 `AGENTS.md`、技能指令要求时委派 |
| 审查方只读 | 用 `tools` 白名单去掉编辑类工具和派发工具；子代理的 `permissionMode` 在 auto 模式下被忽略，不能依赖；Bash 和 PowerShell 仍能写文件，这部分只能靠指令约束 | 只能靠指令约束；定义文件不能覆盖父会话的沙箱与审批设置 |

由此得出三条实现约束：

- Codex 的独立审查必须由受管块中的说明触发，不能指望模型自行委派。
- 受管块计入 Codex 的 32 KiB 合计上限，且排在全局文件之后，全局文件过大时它可能被截掉。受管块应尽量短，`init` 时检查合计大小并在接近上限时报错。
- 每轮检查统一用退出码 2 加 stderr 报告失败，脚本自身出错时同样如此。两个平台都支持这种方式，而其他退出码的处理在两边都没有依据。

### 7.4 实现约束（Python）

- **只用标准库。** 工具只做读写 Markdown、调用 Git、执行检查脚本、输出文本这几件事，不引入第三方依赖。最低版本草案为 3.9，与 Trellis 的要求一致。
- **脚本随仓库走。** 放在 `.trellis/tiny/`，不需要全局安装，版本由仓库固定。不使用上游的 `.trellis/scripts/` 目录，以免覆盖上游文件。
- **受管块只改标记之间的内容。** 标记外的用户内容一律不动；找到多于一对标记或标记不成对时报错退出，不猜测。
- **不解析也不局部修改 TOML。** 标准库不能写 TOML。Codex 的 hook 配置只使用 `.codex/hooks.json`；`.codex/agents/*.toml` 整份写入，不做局部修改。
- **检查脚本用 Python 编写。** 与 CLI 共用同一个解释器，不依赖 Windows 上是否装有 Git Bash。检查脚本每轮都会运行，必须只扫描改动过的文件。
- **解释器名称在初始化时检测。** 不同机器上可用的名称不同（`python`、`python3`、`py`）。Claude Code 侧用带 `args` 的形式直接启动解释器，不经过 shell；由于它没有 Windows 专用字段，解释器名称又因机器而异，草案是把 hook 写入不随仓库共享的 `.claude/settings.local.json`。Codex 侧用 `command` 加 `commandWindows`。
- **用 hook 输入确定工作目录。** Claude Code 在工作树中运行时，`${CLAUDE_PROJECT_DIR}` 仍指向会话启动时的项目根，实际工作目录在 hook 输入的 `cwd` 字段里。脚本用前者定位自身，用后者定位要检查的项目。Codex 的 hook 输入同样带有 `cwd` 字段，它在工作树中的取值待核实。

### 7.5 实现说明（2026-11-18）

源码在仓库根目录，用法见根目录的 `README.md`。共 92 个测试，全部在 Windows 10、Python 3.15 上通过；源码可按 Python 3.9 语法解析，但没有在真实的 3.9 上运行过。

- **快照。** 一个快照是"路径到 Git blob 哈希"的映射：已跟踪内容取自 `git stash create` 生成的提交（不改动暂存列表和工作区），未跟踪文件用 `git hash-object` 计算。这样同一份内容提交前后哈希相同，提交已记录的工作不会被误报为未记录。最初的实现把已跟踪和未跟踪分开计算，测试发现提交后会误报，已改为统一映射。
- **项目检查的接口。** 检查脚本从 stdin 读取 `{"root": ..., "changed_files": [...]}`，改动范围是自上次收尾以来的全部改动（含删除）。退出码 0 为通过，1 为发现问题，其他为脚本自身无法运行。单个检查超时 300 秒，超时按无法运行处理。
- **结束 hook 的防死循环。** 同一失败在没有任何改动的情况下再次出现时放行，并通过 `systemMessage` 提示用户。hook 自身出错时阻止一次；如果输入的 `stop_hook_active` 为真且再次出错，就放行并提示，避免一直无法结束。
- **验证命令的 shell。** `init` 在 Windows 上按 Git Bash、PowerShell 7 的顺序探测，结果写入 `local.json`。Git Bash 的查找顺序是：环境变量 `CLAUDE_CODE_GIT_BASH_PATH`、由 `git --exec-path` 推出的 Git 安装目录、`PATH` 上不在系统目录里的 `bash`（排除 WSL 的 `bash.exe`）。非 Windows 系统使用 `PATH` 上的 `bash`。
- **hook 写法。** Claude Code 用不经过 shell 的直接启动形式，脚本路径写作 `${CLAUDE_PROJECT_DIR}/.trellis/tiny/tt.py`。Codex 用一行命令和脚本的绝对路径，只给路径加引号，这样在 sh、cmd 和 PowerShell 中都能解析。两个文件都含本机路径，因此写入 `.git/info/exclude`。
- **审查子代理的工具清单。** Claude Code 文档写明，清单里列出但当前不可用的工具不会被授予，所以同时列 Bash 和 PowerShell 不会出错；它的 PowerShell 工具优先使用 PowerShell 7。

### 7.6 从上游迁移（2026-11-18）

上游的事实来自其源码：`init` 和 `update` 写入的每个文件都记在 `.trellis/.template-hashes.json`（版本 2 格式，`{"__version": 2, "hashes": {路径: 哈希}}`），上游自己的卸载命令也只处理清单里的文件；`spec/`、`tasks/`、`workspace/` 不在清单里，上游把它们当作用户数据。上游写入的 hook 命令形式是"Python 解释器 + 脚本路径"，Windows 上解释器写作 `python`，其他系统写作 `python3`。

| 条件 | 结果 |
|---|---|
| 项目装有上游，但没加 `--migrate` | `init` 停止，提示先用 `--migrate --dry-run` 预览 |
| 工作区有未提交的改动（`--dry-run` 除外） | 停止，要求先提交或暂存，以便用 Git 检查和回退 |
| 清单缺失，或不是版本 2 格式 | 停止，提示先用上游 CLI 执行 `trellis update` |
| 清单里有 Claude Code 和 Codex 以外的平台文件 | 停止，并列出这些文件 |
| 清单里位于上游目录的文件 | 移入归档目录；清单本身和 `.trellis/.version` 也一并移入 |
| `.claude/settings.json`、`.codex/hooks.json` | 摘掉由 Python 解释器运行已移走脚本的 hook，以及上游的状态栏设置；其余键和用户自己的 hook 保留 |
| hook 的最后一项是已移走的脚本，第一项却不是 Python | 看不出归属，停止并列出这条命令，请用户自己处理 |
| `AGENTS.md` | 摘掉 `TRELLIS:START` 到 `TRELLIS:END` 之间的块，标记不成对时停止 |
| `.codex/config.toml` | 不动；上游留下的两项设置不影响 tiny-trellis，记入 `MIGRATION.md` |
| 名字以 `trellis` 开头、但不在清单里的平台文件 | 原地不动，在输出和 `MIGRATION.md` 中逐个列出，请用户判断 |
| 无法解析的旧 `task.json` | 不中断迁移；在旧任务索引中按目录名列出并注明原因，文件本身不改 |

上游的 `.trellis/.gitignore` 会忽略 `.agents/`、`*.tmp` 等路径，归档进 `.trellis/` 后部分文件会因此进不了 Git。所以归档目录里写入一个只有 `!*` 的 `.gitignore`，让其中的文件全部可以提交。

**hook 归属的判断比上游更严。** 上游卸载时只看命令的最后一项是不是它的脚本，于是一条以脚本路径结尾的 `echo` 也会被当成上游的。实现中改为同时要求第一项是 Python 解释器，看不出归属时停下，不做猜测。

**真实数据验证。** 在上游 Trellis 仓库的临时克隆上运行：它的清单有 228 项、涉及 7 个平台，迁移按设计停止并列出其他平台的文件。把清单限定为 Claude Code 和 Codex 后迁移成功，归档 115 个文件，摘掉 8 个 hook 和 `AGENTS.md` 中的块，之后状态行正常输出。这次运行发现了两个测试没有覆盖的情况，已按上表处理：243 个旧任务中有 10 个 `task.json` 不是合法 JSON（早期版本的值没加引号），以及上游旧版本留下、不在清单里的 trellis 技能和命令。修复后在真实副本上的复验被中断，没有完成；这两处修复由测试覆盖。

### 7.7 技能（2026-11-19）

两个平台的技能格式相同：一个目录里放一个 `SKILL.md`，头部写 `name` 和 `description`，可以附带只在需要时读取的参考文件。

| | Claude Code | Codex |
|---|---|---|
| 位置 | `.claude/skills/<名称>/SKILL.md` | `.agents/skills/<名称>/SKILL.md` |
| 常驻上下文的内容 | 名称和描述，每条最多 1,536 字符，每轮都计入上下文 | 名称、描述和路径；整个列表默认最多占上下文窗口的 2% |
| 正文何时加载 | 调用时加载，之后一直留在上下文中；压缩后重新注入，每个技能最多 5,000 token | 选中时读取 |
| 只允许用户调用 | 头部写 `disable-model-invocation: true`，描述也不再常驻 | `agents/openai.yaml` 中写 `policy.allow_implicit_invocation: false`；描述是否仍然列出，文档未说明 |

| 技能 | 何时用 | 对应的上游技能 | 调用方式 |
|---|---|---|---|
| `tt-clarify` | 需求里有只有用户能做的选择，或验收标准不清：一次问一个问题，写下目标和验收标准 | brainstorm | 模型自动调用 |
| `tt-task` | 跨会话任务的创建、恢复、交接和结束 | start、continue | 模型自动调用 |
| `tt-review` | 高风险改动的独立审查：派发审查子代理，处理回复，没有子代理时退回自检 | check | 模型自动调用 |
| `tt-record` | 用户确认的决定、修复得出的经验、规则被替换时，更新规范和索引 | update-spec、break-loop | 模型自动调用 |
| `tt-digest` | 把迁移留下的旧任务和旧日志按主题整理成规范 | mini-trellis 的 session-insight | 仅用户调用 |
| `tt-bootstrap` | 根据仓库写出第一批规范和索引 | spec-bootstrap | 仅用户调用 |

不做成技能的上游步骤：before-dev（写代码前读规范）由受管块中的一句规则覆盖；finish-work 是必做步骤，留在受管块里由 CLI 强制执行，放进技能就要依赖模型记得去调用。

**安装方式。** 每个技能只有一份源文件，头部只写两个平台都读的 `name` 和 `description`。`init` 按平台写入：Claude Code 版本给仅用户调用的技能在头部加一行，Codex 版本原样写入，另给这两个技能加 `agents/openai.yaml`。这样不会把一个平台的专用字段写给另一个平台。

**常驻篇幅。** 受管块约 2,200 字符，4 个模型可自动调用的技能描述合计约 850 字符，合计约 3,040 字符，比原先受管块单独的约 3,660 字符少 17%，未计各平台列表本身的格式开销。省得不多，因为受管块要指明什么情况用哪个技能，而每个技能的描述也要写清触发条件。主要收益在于步骤正文只在用到时才加载：6 个技能的正文合计约 9,500 字符，若全部写进受管块，每个会话都要付这笔成本。

**技能中的固定约定（2026-11-19 复查后加入）。**

- **跨会话任务按轮更新，不等会话结束。** 模型看不到会话何时结束，用户可能直接关掉窗口，所以"会话结束前更新任务文件"这一步实际上常被跳过。改为在推进了任务的每一轮结束时更新"已完成""下一步""决定"，并为本轮已验证的工作运行 `finish`。受管块的收尾规则也去掉了"会话结束前"，改为"包括跨会话任务中每个已验证的步骤"。
- **被替换文件的标记格式固定。** 旧文件第一行写 `> Superseded by [新文件](新文件) on YYYY-MM-DD.`，其余内容不动，搜索时能分辨哪些文件仍然有效。
- **调研笔记放在 `.trellis/spec/research/`。** 知识索引只列规则文件，调研笔记由规则链接，避免把证据和规则混在一起。
- **整理过的旧任务要标记。** `tt-digest` 处理完一个上游任务后，在 `upstream-tasks.md` 中它那一行末尾追加 `— digested into [文件](文件) on YYYY-MM-DD`，或 `— digested, nothing kept, on YYYY-MM-DD`，下次跳过；这个文件由迁移生成，标记它不会改动原始材料。
- **首批规范每个文件最多 15 条规则。** 细节移入调研笔记。

**测试覆盖。** 技能源文件头部字段、名称与目录一致、描述长度不超过 Claude Code 的上限；受管块和技能正文里提到的技能都存在，受管块提到了全部技能；两个平台的安装结果和仅用户调用的标记。技能在真实会话中能否按描述被正确触发，没有测试。

### 7.8 安装与升级（2026-11-19）

安装方式参照上游 Trellis，只是执行的任务管理逻辑不同。上游用 `npm install -g` 装全局命令，在项目里运行 `trellis init`，升级用 `trellis update`。tiny-trellis 的流程是 `git clone` 之后在仓库里运行 `./tt install`（cmd 和 PowerShell 中是 `.	t install`），得到全局命令 `tt`；安装和升级项目都用 `tt init`，由项目里有没有 `.trellis/tiny/config.json` 决定走哪条路。

**全局命令不经过 pip。** 仓库根目录自带两个启动脚本：`tt` 供 Git Bash、macOS、Linux 使用，`tt.cmd` 供 cmd 和 PowerShell 使用。它们按 `python3`、`python`、`py -3` 的顺序找第一个 Python 3.9+，这与 hook 选解释器的顺序一致；版本检查会筛掉 Windows 上只是应用商店占位程序的 `python3`。`tt install` 把两个小启动脚本写进 PATH 上的目录（Windows 上是解释器的 `Scripts` 目录，其他系统是 `~/.local/bin`），脚本里写死解释器和本仓库 `tt.py` 的绝对路径，所以 `git pull` 之后全局命令随之更新。不需要 pip，不联网，也不产生构建目录。启动脚本带有标记行，`tt install` 不会覆盖没有该标记的 `tt`，`tt uninstall` 只删除带标记的启动脚本。早先曾改用 pip 的可编辑安装，已换成这种方式并删除了 `pyproject.toml`。

**不自带也不自动安装 Python。** 找不到可用的 Python 时，启动脚本说明原因并给出 python.org 的下载地址后退出。自带 Python 要为每个平台各维护一份运行时，与轻量工具的定位不符；自动安装 Python 会改动本机软件，不应默默进行。是否提供"列出安装命令、经用户确认后执行"的选项，待定。

**全局命令和项目副本。** 全局的 `tt` 只负责安装和升级，hook 调用的始终是项目里的 `.trellis/tiny/tt.py`。这与上游把脚本复制进 `.trellis/scripts/` 的做法一致：换一台机器，或者另一个项目停在旧版本，都不会互相影响。版本号只在 `ttlib/__init__.py` 中写一次。

| 情况 | 上游 `trellis update` | `tt init` |
|---|---|---|
| 未安装 | 交互询问或按参数选平台 | 默认两个平台都装，参数可以只装一个 |
| tt 写过、你没改过的文件 | 直接覆盖 | 同上，旧文件先备份 |
| 你改过的文件 | 交互询问覆盖、跳过或另存 `.new` | 停下并列出；`--force` 备份你的版本后覆盖，`--keep` 保留你的版本 |
| 你删掉的文件 | 不重建 | 技能和审查子代理不重建；tt 自己的代码会恢复，否则 hook 无法运行 |
| 新版本不再使用的文件 | 按迁移清单校验哈希后删除 | 没改过的移入备份目录，改过的留在原处并提示 |
| 项目版本比本机 tt 新 | 拒绝，`--allow-downgrade` 可强制 | 同上 |
| 升级前的备份 | `.trellis/.backup-<时间>/` | 被替换和退役的文件备份到 `.trellis/tiny/.backup-<时间>/` |

**哪些文件按所有权管理。** tt 整体写入的文件（项目副本代码、技能、审查子代理、`.trellis/tiny/.gitignore`）记入 `manifest.json`，哈希计算时忽略 CRLF 与 LF 的差别，避免 `autocrlf` 的检出被误判为手动修改。在原处编辑的文件（`AGENTS.md` 的受管块、`CLAUDE.md` 的导入行、hook 配置、`.git/info/exclude`）不进清单，仍按 4.4 和 7.3 的合并规则处理。

**升级后的基线。** 升级前工作区没有未记录的改动时，升级后重新记录基线，状态行不会把升级本身误报为未记录的工作；升级前已有未记录的工作时，基线不动，以免把这些工作藏起来。

**验证。** 测试覆盖上表各行和添加平台的情况，以及启动脚本：在临时目录里执行 `tt install`，分别从 cmd 和 Git Bash 运行装好的 `tt`，确认它运行的是本仓库；已有别人的 `tt` 时拒绝覆盖，`tt uninstall` 只删自己的启动脚本。实测中发现，本会话的环境设置了 `NoDefaultCurrentDirectoryInExePath`，cmd 因此不在当前目录里找 `tt.cmd`，所以文档统一写作 `.	t install`。没有写入本机 PATH 上的真实目录。

## 8. 已确认的决策

- 首要削减上下文成本；知识记忆是必须保留的核心。
- 流程关卡交给模型判断，用户可显式声明；未声明时完全由模型判断。
- 小任务直接执行，但要记录"为什么改"和"验证结果如何"。
- 独立审查由没看过实现过程的独立上下文承担，仅用于高风险改动或用户要求时。
- 兼容 `.trellis/` 目录，首次运行对历史内容做归档。
- 当前为单人使用，首批平台为 Claude Code 和 Codex。
- 实现语言为 Python，仅用标准库，不依赖 Node.js。
- 每轮结束时自动运行脚本能判定的检查，不做成开关；需要读代码判断的要求不在每轮强制。
- 全局提示词不在 tiny-trellis 的范围内；管理方案作为补充提示词写入项目级提示词。
- 受管块正文用英文，与全局提示词一致。
- Windows 上执行验证命令的 shell 默认用 Git Bash，没有时退回 PowerShell 7。
- 使用技能承载操作步骤，共 6 个，其中 `tt-digest` 和 `tt-bootstrap` 仅用户调用；受管块只保留每次都适用的规则（2026-11-19）。
- 安装方式参照上游 Trellis：`git clone` 后在仓库里运行 `tt install` 得到全局命令 `tt`，默认使用本机的 `python3`，不经过 pip；在项目里运行 `tt init`，已安装的项目再运行 `tt init` 即为升级（2026-11-19）。

由最后一条推出、尚待确认的两点：

- 每轮检查只运行项目登记的检查脚本，项目没有登记时不安装结束 hook。原先设想的硬规则清单、20 条上限和规则编号全部取消。
- 受管块以项目 `AGENTS.md` 为唯一载体，Claude Code 通过 `CLAUDE.md` 中的导入行读取。

起草受管块正文时做出的三点调整，已于 2026-11-18 确认：

- 状态行始终输出，并携带本机的命令前缀。
- 长文知识以 `.trellis/spec/index.md` 为索引。
- 日志按每次收尾一条记录，而不是每个任务一条，否则跨会话任务的中间会话会被误报为"有未记录的改动"。
